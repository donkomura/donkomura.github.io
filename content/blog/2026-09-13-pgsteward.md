近年、データベースを作成・管理する主体は人間から AI agent に移りつつある。
Databricks の Lakebase の論文[^lakebase]によると、Lakebase では 1 日あたり 1,000 万を超えるデータベースが作成・管理されていて、AI agent が作るデータベースの数は人間の約 4 倍に達しているという。
この規模になると、データベースまわりの設定を人間が 1 つずつ見直していく運用は成り立たない。
コネクションプーラーの設定もその例外ではない。

そこで、複数のプーラーのプールサイズを 1 箇所の台帳でまとめて管理し、需要に応じて自動で払い出すコネクションプーラー PgSteward を設計した。
この記事では、既存のプーラーで何が足りないのか（why）と、PgSteward が何をするのか（what）をまとめる。
どう実現しているか（how）の詳細は、実装と検証が進んだ段階で別の記事にする。

## 既存のコネクションプーラーで何が足りないのか

PostgreSQL は接続 1 本ごとにプロセスを作り、受け入れる本数の上限を `max_connections` で決めている。
アプリケーションが増えると接続の合計はすぐにこの上限に近づくので、アプリケーションとデータベースの間にコネクションプーラーを置き、少数の接続を使い回すのが一般的である。
PostgreSQL では [PgBouncer](https://github.com/pgbouncer/pgbouncer) が広く使われていて、マルチコア対応やシャーディングを足した [PgCat](https://github.com/postgresml/pgcat) や、クラウドで大量のクライアント接続を捌く [Supavisor](https://github.com/supabase/supavisor) もある。

これらのプーラーでは、PgBouncer が登場した 2007 年から今日まで、プールサイズの上限は設定ファイルに書く静的な値として扱われてきた。
上限を固定値で持つと、台数・テナント数・需要のいずれかが変わるたびに値が合わなくなる。
以下では、この固定値が問題になる場面を 3 つ挙げる。

### プーラーの台数が変わる

プーラーは単一障害点になるので、冗長化のために最低でも 2〜3 台は並べる。
アプリケーションと同じホストに同居させる構成なら、アプリケーションが 10 台から 50 台にオートスケールすればプーラーも 50 台になる。
既存のプーラーにはクラスタ全体の合計を書く場所がない（[pgbouncer#103](https://github.com/pgbouncer/pgbouncer/issues/103)）ので、1 台あたりの上限を `max_connections` から人間が割り算で決める。
台数が増えたときに書き換えなければ、データベースへの接続の合計は台数に比例して増え、`max_connections` を超えて接続エラーになる。
逆に安全側に小さく書けば、データベースに余裕があっても並行度が落ちる。

割り算で決めた値は、台数が固定でも需要の偏りには合わない。
ロードバランサの偏りで 1 台に需要が集中すると、その 1 台は上限に達してクライアントが待ち、他の台では枠が遊ぶ。

### テナントの需要が混雑時にぶつかる

PgBouncer は接続先データベースと接続ユーザーの組ごとにプールを分けるので、マルチテナントな SaaS ではテナントの数だけプールができる。
その中には、夜間バッチやプロモーションで急にコネクションを大量に消費するテナントが含まれる。
合計の上限だけを決めて先着順で使わせると、こうしたテナントが空きを取り切ったときに、他のテナントへ接続が回らなくなる。
実際に、`max_db_connections = 10` をユーザー A / B / C で共有して同じ負荷をかけると、A だけが接続を取れて C はタイムアウトを繰り返すという挙動が報告されている（[pgbouncer#131](https://github.com/pgbouncer/pgbouncer/issues/131)）。
バッチのトランザクションは数秒、オンライン API は数ミリ秒かかるので、同じキューに並べると API の応答時間はバッチのトランザクションの長さまで伸びる。

テナントごとに固定サイズで分ければ下限は守れるが、需要のないテナントの枠が遊ぶ。
また PgBouncer は、使われなくなったテナントのプールを管理用の情報として持ち続ける（[pgbouncer#1085](https://github.com/pgbouncer/pgbouncer/issues/1085)）。
テナントが増え続ける環境では、この情報も増え続ける。

### 他の接続元を締め出せない

データベースには、プーラー以外にも管理者の作業や監視が接続する。
プーラーが `max_connections` まで使い切ると、これらの接続元が締め出される。
一方で、1 本あたり数 MB のメモリを消費するコネクションを遊ばせるのも無駄なので、プーラーの接続の合計は他の接続元のぶんを残したうえで、できるだけ使い切りたい。

### 求められる性質

ここまでの問題をプーラーに求める性質として並べ直すと、次の 4 つになる。

- 管理者や監視など他の接続元を締め出さない
- API とバッチのように用途を分けたとき、各用途が確保できる接続数の下限を保証する
- 空いたコネクションを遊ばせない
- クエリの経路にホップを増やさない

しかもこれらを、プーラーの台数やテナント数が変わっても、設定を書き換えずに満たしたい。
固定サイズで分ける方式は下限を保証できるが、空きが遊ぶ。
合計だけを決めて先着順で使わせる方式は空きが遊ばないが、下限がない。
Supavisor はテナントごとに所有ノードを 1 つ決めて接続を集約するので、台数を増やしても接続は増えないが、所有ノードへの中継のぶんホップが増える。
既存のプーラーはどれも、このうちの一部しか満たせていない。

## PgSteward は何をするのか

PgSteward は、プールサイズの上限を設定値として持たない。
代わりに、1 箇所の台帳から需要に応じて期限付きで払い出す予算として扱う。
台数やテナント数の増減だけなら総量を割り直せば対応できるが、需要の偏りや時間帯による入れ替わりには割り算では追随できない。
需要に追随しつつ下限も守るには、接続を張る前に枠を予約する必要があり、予約するには全体の割当を 1 箇所で持つ台帳が要る。

### 総予算をデータベースから求める

払い出せる総量を総予算と呼ぶ。
総予算は設定ファイルに書かず、`max_connections` から予約枠と他の接続元のぶんを引いて、データベースの設定から求める。
人間が台数で割り算をする場面はなくなり、他の接続元のぶんは最初から総予算の外に置かれる。

### 最低保証と余剰で取り分を決める

テナントには最低保証・上限・重みの 3 つを宣言させる。
PgSteward は最低保証を先に確保し、残った余剰を、需要のあるテナントへ重み付き max-min fair で配る。
max-min fair は、少なく要求しているテナントを先に満たし、余った分を多く要求しているテナントで分け合う方式である。
最低保証は API とバッチのように守りたい用途にだけ宣言し、それ以外のテナントは最低保証 0 のまま余剰を分け合う。

例えば総予算 100 本、API を捌く `web` の最低保証 30 本、夜間バッチを走らせる `worker` の最低保証 10 本で、`web` が 60 本、`worker` が 90 本を要求したとする。
最低保証の 30 本と 10 本を先に確保し、余剰 60 本を残りの要求（`web` 30 本、`worker` 80 本）へ重み等分で配ると各 30 本になる。
`web` は 60 本で要求を満たし、`worker` は 40 本になる。

{{ figure(src="/assets/2026-09-13-pgsteward-allocation.png", alt="総予算 100 本の配分例", caption="最低保証を先に確保し、余剰 60 本を需要のあるテナントへ配る") }}

この配り方は、時間帯で需要が入れ替わるときにも追随する。
日中は `worker` の需要がないので、枠はほぼすべて `web` に渡る。
夜間にバッチが始まると、枠は `web` から `worker` へ移る。
バッチの最中に API の需要が戻れば、上の例のとおり `web` は 60 本を得て、待つのは `worker` だけになる。
総量が足りなければ誰かは待つが、PgSteward では最低保証によって待つ側を選べる。

{{ figure(src="/assets/2026-09-13-pgsteward-rebalance-over-time.png", alt="時間帯による配り直し", caption="日中は API に、夜間はバッチに枠が寄り、深夜に API の需要が戻れば逆向きに配り直す") }}

払い出しは需要のあるところにしか行かないので、テナントを登録しただけではプールは作られない。
プールの数は、登録したテナントの数ではなく、同時にクエリを投げているテナントの数に比例する。

### 割当を決める coordinator とクエリを通す proxy

台帳を 1 箇所で持つと、その主体をクエリの経路に置くかどうかが問題になる。
経路に置けば、割当を決めるための通信の遅延がそのままクエリの遅延に乗る。
そこで PgSteward は役割を 2 つに分けた。
proxy はプーラーの本体で、アプリケーションからの接続を受け、データベースへ接続を張ってクエリを通す。
coordinator は、どの proxy がどのテナントのために何本張ってよいかを決める。
運用するものを増やさないために、両者は同じバイナリを起動時の指定で振り分ける。

    Proxy ==>|"クエリ"| DB[("PostgreSQL")]
    Proxy -.->|"需要の報告"| Coord["coordinator<br/>割当表"]
    Coord -.->|"枠の払い出し・回収"| Proxy
    Coord -.->|"接続の確認・上限の書き換え"| DB
{% end %}

実線がデータの経路で、アプリケーション、proxy、PostgreSQL の 1 本道である。
クエリとその応答は coordinator を通らないので、Supavisor のような中継のホップは増えない。
払い出しは台数で割るのではなく需要で決まるので、proxy を 4 台から 8 台に増やしても総予算は 100 本のままで、設定は何も変えない。
200 台に 100 本を配る構成も、既存のプーラーでは 1 台あたり 0.5 本と書く必要があって表現できないが、PgSteward では需要のある proxy に枠が集まる形で成立する。

### coordinator に依存しすぎない

台帳を持つ主体を置くと、その主体が止まったときの振る舞いが問題になる。
coordinator が止まったときにクエリまで止まるなら、固定値を書く既存のプーラーより悪くなる。
PgSteward では、coordinator が止まっても、すでに張られている接続でクエリが流れ続け、最低保証の範囲で新しい接続も張れる。
このとき PgSteward は、止まった時点の払い出しを上限とする固定上限のプーラーに縮退する。

接続数の上限そのものは、PgSteward が正しく動いているかに頼らず、データベースに検査させる。
proxy はテナントごとのロールで接続を張り、coordinator は各ロールの `CONNECTION LIMIT` を払い出しに合わせて書き換える。
また、割当表は PostgreSQL の接続の一覧（`pg_stat_activity`）から組み立て直せるキャッシュとして扱うので、割当表のために別の複製の仕組みは持たない。

## まとめ

既存のコネクションプーラーの課題は、プーラーの台数の増加、テナント数の増加、混雑時の取り分のどれもが、有限のコネクションをどう配るかという問題に行き着き、その根はプールサイズを設定ファイルに書く静的な値として扱っていることにあった。
PgSteward は、プールサイズを 1 箇所の台帳から需要に応じて払い出す予算として扱う。
総予算はデータベースから求め、守りたい用途には最低保証を宣言させ、余剰は需要のあるところへ配る。
割当を決める coordinator はクエリの経路に置かず、止まっても固定上限のプーラーに縮退するだけでクエリは止まらない。

枠を proxy の間で動かす途中に接続の合計が総予算を超えないようにする手順や、枠を手放す速さの調整といった how の部分は、複数台での実測とあわせて改めて記事にしたい。

[^lakebase]: Jasraj Dange et al., [Lakebase: Serverless Postgres over Open Lake Storage](https://www.vldb.org/pvldb/vol19/p4385-pandis.pdf), PVLDB Vol. 19.
